## 2. Descripción funcional
* **Descripción:** Sistema silencioso subyacente que recopila más de 500 tipos de micro-eventos en tiempo real (Dónde hace pausa en un video, qué fragmentos de texto subraya, cuántas veces borra una respuesta antes de enviarla, tiempo de lectura por página).
* **Objetivo:** Construir el "Data Moat" (Ventaja competitiva por datos) de EDUCACION OS. Alimentar el Gemelo Digital del Estudiante (DTL) con billones de datapoints puros para entrenar modelos de IA propietarios en el futuro.
* **Alcance:** Tracking SDK embebido en el frontend, Cola de ingesta distribuida, Data Warehouse columnar.
* **Actores:** Estudiante (Generador pasivo), Sistema de Ingesta (Consumidor).

## 3. Contexto
* **Precondiciones:** 
  1. Frontend montado con el provider de Telemetría activo.
  2. Consentimiento de cookies/datos (RF-020) aceptado por el apoderado.
* **Disparador:** Cualquier micro-interacción en el navegador (Scroll, Clic, Hover, Video Pause).
* **Postcondiciones:** Logs inyectados en la base de datos columnar en crudo.

## 6. Flujo funcional
### Flujo principal (Ingesta Batch por Cliente)
1. El estudiante lee un texto. Subraya 3 párrafos y pausa 2 veces.
2. El SDK del Frontend no envía las peticiones inmediatamente (para no matar la red). Las agrupa en memoria (Batching).
3. Cada 5 segundos o al salir de la página (`beforeunload`), el SDK hace un solo POST `/api/v1/telemetry/collect` con el batch de eventos usando `navigator.sendBeacon()`.
4. El Edge Worker (Cloudflare Workers o Gateway Node) intercepta el request.
5. El evento no va a PostgreSQL (colapsaría). Va directamente a una cola **Kafka / PubSub / Redis Streams**.
6. Un consumidor asíncrono toma los eventos masivos y los vuelca en una Base de Datos Columnar (ClickHouse / BigQuery).

### Flujos de excepción
* **FE-01: Pérdida de Conexión (Offline):** Si el alumno pierde WiFi en el tren pero sigue en la PWA, los micro-eventos se guardan en IndexedDB y se sincronizan masivamente cuando vuelve la señal.

## 8. Reglas de negocio
* **RN-001 (Fire and Forget):** La API de telemetría debe responder en menos de 20ms. Jamás debe procesar validaciones pesadas o reglas de negocio de negocio de manera síncrona, para no degradar el rendimiento del UX.
* **RN-002 (Costo de Storage):** Conservar micro-eventos granulares es caro. Tras 6 meses, los datos crudos de ClickHouse deben ser consolidados (Agregados a nivel día/mes) y los crudos se envían a Cold Storage (AWS Glacier / GCS Archive) por retención histórica económica.

## 9. Permisos y seguridad
* **PII Stripping:** La telemetría no debe llevar el nombre, correo o contraseña de usuario, NUNCA. Si un evento es `INPUT_TYPING`, no se captura lo que el usuario escribió (violación de privacidad), solo se captura el *keystroke rate* (velocidad de tipeo).

## 10. Persistencia
* **Tablas/Colecciones:** Arquitectura OLAP obligatoria (Postgres se corrompería con este nivel de writes). Integración con ClickHouse.

## 11. Integraciones
* **Infraestructura Data:** Upstash Kafka, Google Cloud Pub/Sub o Amazon Kinesis para el pipeline de ingesta.

## 14. Criterios de aceptación (BDD)
* **CA-01: Performance de Ingesta (High Throughput)**
  * *Given* que 10,000 alumnos están conectados simultáneamente
  * *When* los clientes despachan batches cada 5 segundos
  * *Then* la API de Ingesta no debe superar los 50ms de latencia p99, validando la separación del Event Loop principal.
* **CA-02: Flush en Cierre de Pestaña**
  * *Given* que el usuario tiene 40 eventos en cola en la memoria de React
  * *When* cierra violentamente la pestaña (Close Tab)
  * *Then* el sistema debe lograr enviar el payload exitosamente usando la Web API `navigator.sendBeacon()` sin ser cancelado por el navegador.
