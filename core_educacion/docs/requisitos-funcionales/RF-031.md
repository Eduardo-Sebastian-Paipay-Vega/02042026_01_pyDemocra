## 2. Descripción funcional
* **Descripción:** Emisión de certificados, diplomas y constancias de notas utilizando credenciales verificables criptográficamente en una Blockchain (Ethereum Layer 2 o Polygon). Otorga al estudiante propiedad absoluta sobre su historial académico (Self-Sovereign Identity - SSI), permitiéndole demostrar sus logros a universidades o empleadores sin depender de que el colegio original siga existiendo.
* **Objetivo:** Erradicar la falsificación de certificados educativos y eliminar la burocracia en el proceso de admisión universitaria.
* **Alcance:** Smart Contracts para emisión, Wallet digital en la app móvil del alumno, portal de verificación pública.
* **Actores:** Institución (Emisor/Issuer), Estudiante (Poseedor/Holder), Universidad/Empleador (Verificador/Verifier).

## 3. Contexto
* **Precondiciones:** 
  1. El estudiante finalizó un curso o etapa académica oficial.
  2. Aprobación final registrada por el Director Académico.
* **Disparador:** El colegio emite el lote anual de certificados de graduación.
* **Postcondiciones:** Un Token No Fungible (NFT) tipo *Soulbound* o una Credencial Verificable W3C es acuñada (minted) y enviada a la wallet del estudiante.

## 4. Entradas
| Parámetro | Tipo | Obligatorio | Validaciones |

## 6. Flujo funcional
### Flujo principal (Emisión SSI)
1. Fin de año. El Director presiona "Emitir Certificados Oficiales".
2. NestJS recopila las notas finales y construye un objeto JSON siguiendo el estándar *W3C Verifiable Credentials (VC)*.
3. El sistema firma el objeto JSON usando la Clave Privada ECDSA de la Institución.
4. El sistema sube el archivo JSON firmado a IPFS (InterPlanetary File System) para almacenamiento inmutable y descentralizado.
5. NestJS llama a un Smart Contract (vía `ethers.js` o `viem`) para emitir un evento en la Blockchain que vincula el hash de IPFS con el `DID` del colegio y el del alumno.
6. El alumno abre su App Móvil (Wallet) y ve su nuevo Certificado. Puede compartir un "Zero-Knowledge Proof" a una universidad para demostrar que terminó la secundaria sin revelar sus notas exactas si así lo desea.

### Flujos alternativos
* **FA-01: Verificación de Terceros:** La Universidad de Harvard recibe el CV del alumno. Escanean un código QR. El portal de EDUCACION OS verifica la firma criptográfica en la Blockchain, confirmando que el colegio emitió ese certificado y no ha sido alterado.

### Flujos de excepción
* **FE-01: Revocación:** Si se descubre un fraude masivo (ej. hackeo de notas antes de la emisión), el Director usa su llave maestra para interactuar con el Smart Contract y añadir el `credential_hash` a la Lista de Revocación (CRL). La próxima vez que alguien escanee el QR, saldrá "CERTIFICADO INVÁLIDO".

## 8. Reglas de negocio
* **RN-001 (Soulbound Tokens):** Los certificados académicos no se pueden vender ni transferir. Si se implementan como NFTs, deben ser estrictamente del tipo SBT (Soulbound Tokens), lo que significa que el Smart Contract bloquea la función de `transferFrom()`.
* **RN-002 (Gas Station):** Los colegios y estudiantes no deben lidiar con criptomonedas para pagar los costos de red (Gas Fees). EDUCACION OS implementa un "Paymaster / Gas Station Network" (ERC-4337) que subsidia el costo de la transacción en background.

## 9. Permisos y seguridad
* **Custodia de Llaves (KMS):** La clave privada del colegio para emitir certificados jamás se guarda en texto plano en la BD. Se gestiona mediante AWS KMS o Google Cloud KMS usando HSMs (Hardware Security Modules). Ni siquiera los ingenieros de EDUCACION OS pueden extraer la llave privada del colegio.

## 10. Persistencia
* **Tablas/Colecciones:** IPFS para almacenamiento del JSON de notas. Polygon (L2) o Arbitrum para el registro inmutable de la firma. Postgres solo guarda el registro de la operación.

## 11. Integraciones
* **Web3 SDK:** `ethers.js`, o infraestructura de billeteras como Magic.link / Web3Auth para que los estudiantes no tengan que guardar frases semilla (Seed phrases) complejas.

## 12. Auditoría
* La Blockchain es, por definición, el registro de auditoría perfecto. Cualquier intento de alterar una nota en el certificado cambiará el Hash criptográfico, rompiendo la validación instantáneamente.

## 13. Notificaciones
* Notificación Push al alumno: "Tu Diploma Oficial ha sido acuñado en la Blockchain. Ya es tuyo para siempre".

## 14. Criterios de aceptación (BDD)
* **CA-01: Verificación de Inmutabilidad**
  * *Given* un certificado emitido válido
  * *When* un tercero malicioso intercepta el JSON y cambia la nota de "C" a "A"
  * *Then* el Verificador W3C debe calcular un Hash diferente al almacenado en la Blockchain, devolviendo un error rojo de "FIRMA CRIPTOGRÁFICA CORRUPTA".
* **CA-02: Revocación por Emisor**
  * *Given* un certificado válido
  * *When* el colegio firma una transacción de revocación
  * *Then* los portales públicos de verificación deben reflejar inmediatamente el estado "Revocado" leyendo el registro del Smart Contract.
