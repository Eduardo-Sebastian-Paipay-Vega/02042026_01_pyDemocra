## 2. Descripción funcional
* **Descripción:** Sistema de Alerta Temprana (Early Warning System - EWS) que utiliza Machine Learning (ej. Random Forest / XGBoost) para analizar patrones de comportamiento (caída en notas, inasistencias consecutivas, reducción de login time) y predecir la probabilidad de que un estudiante abandone la institución en los próximos 30 días.
* **Objetivo:** Proactividad extrema. Permitir que los tutores o el departamento de bienestar intervengan ANTES de que el alumno pida su retiro, salvando el LTV (Life Time Value) del cliente y el futuro del estudiante.
* **Alcance:** Ingesta de datos diarios, inferencia del modelo, y actualización del "Semáforo de Riesgo" en el perfil del alumno.
* **Actores:** Sistema ML (Ejecutor), Tutor/Psicólogo (Receptor de la Alerta).

## 3. Contexto
* **Precondiciones:** 
  1. Data Mart `student_daily_aggregates` (RF-015) poblado.
  2. Modelo pre-entrenado exportado en formato ONNX o API externa (Vertex AI / SageMaker).
* **Disparador:** CronJob nocturno de inferencia (`0 4 * * *` - 4:00 AM).
* **Postcondiciones:** Campo `dropout_risk_score` actualizado en la BD. Si el riesgo > 75%, se dispara alerta crítica.

## 6. Flujo funcional
### Flujo principal (Inferencia Batch Nocturna)
1. El Scheduler dispara el Job `EWS_InferenceJob`.
2. El worker extrae de Postgres/ClickHouse un dataset con el comportamiento de los últimos 30 días de todos los estudiantes activos.
3. Transforma los datos en un vector de características (Feature Engineering en memoria).
4. Pasa el vector al modelo (vía API a Vertex AI o un microservicio Python con ONNX Runtime).
5. El modelo devuelve las probabilidades (`risk_score`) y los motivos principales de esa decisión.
6. El worker realiza un Upsert masivo en Postgres tabla `student_risk_profiles`.
7. Si un estudiante salta del umbral "Bajo" al umbral "CRÍTICO" (Score > 0.85), se genera un evento en el Notification Bus dirigido al Psicólogo asignado y al Director.

### Flujos alternativos
* **FA-01: Intervención Logueada:** Cuando un Psicólogo recibe la alerta, debe abrir un "Ticket de Intervención". Al hacerlo, el riesgo visual no baja inmediatamente (el modelo decide), pero el sistema oculta temporalmente la campana de alarma (Acknowledge state).

### Flujos de excepción
* **FE-01: Data Drift (Caída del modelo):** Si repentinamente el modelo clasifica al 90% del colegio como "Riesgo Crítico" (Posible error por un feriado no mapeado), una regla heurística bloquea el envío masivo de alertas al detectar la anomalía y pide recalibración.

## 8. Reglas de negocio
* **RN-001 (Explainable AI - XAI):** No basta con decir "El alumno X se irá". Es obligatorio por diseño funcional que el modelo de ML exponga el `top_factors` (Ej. Factor 1: -30% interacción en foros, Factor 2: Baja calificación en curso core). La IA debe ser explicable para que el humano pueda actuar.
* **RN-002 (Feedback Loop):** Si el psicólogo logra retener al alumno, marca la intervención como "Exitosa". Este dato se guarda en `ml_training_feedback` para re-entrenar el modelo el próximo semestre.

## 9. Permisos y seguridad
* **Sensibilidad Extrema:** Predecir deserción puede conllevar sesgos (Bias). Esta tabla está blindada con RLS para que solo `PRINCIPAL`, `PSYCHOLOGIST` y el motor de IA puedan leerla. Profesores regulares NO ven este score para evitar el Efecto Pigmalión (Profecía autocumplida).

## 10. Persistencia
* **Tablas/Colecciones:** `student_risk_profiles`.
* **Escritura Batch:** Se usa `INSERT ... ON CONFLICT (student_id) DO UPDATE` masivo (Upsert de Postgres) para procesar miles de inferencias en una sola transacción.

## 11. Integraciones
* **Motor ML:** Python Microservice (FastAPI + Scikit-Learn/ONNX) u hospedaje serverless en Vertex AI / AWS SageMaker.

## 12. Auditoría
* Tabla `ews_predictions_history` guarda el snapshot diario del score para graficar curvas de tendencia.

## 13. Notificaciones
* Correo de alta urgencia al departamento de bienestar: "[ALERTA EWS] El estudiante Juan Pérez ha entrado en riesgo crítico de deserción".

## 14. Criterios de aceptación (BDD)
* **CA-01: Heurística de Anomalía (Kill Switch)**
  * *Given* que el modelo por error infiere que el 100% de la escuela desertará
  * *When* el worker intenta actualizar la tabla
  * *Then* la regla de negocio aborta la actualización y dispara un Webhook a los ingenieros de DevOps alertando "Data Drift Crítico en modelo EWS".
* **CA-02: Explicabilidad (XAI)**
  * *Given* que un usuario tiene 85% de riesgo
  * *When* el director abre su perfil 360
  * *Then* debe ver un semáforo rojo Y una lista de viñetas indicando el "Por qué" la IA tomó esa decisión, leídos desde `top_factors`.
