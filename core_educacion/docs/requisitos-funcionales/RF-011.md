## 2. Descripción funcional
* **Descripción:** Sistema de mensajería instantánea 1-a-1 y grupal que permite a estudiantes y docentes comunicarse dentro del ecosistema de la plataforma. Todo mensaje es auditado y analizado por IA en tiempo real para bloquear cyberbullying, lenguaje inapropiado o grooming.
* **Objetivo:** Facilitar la resolución de dudas académicas en tiempo real garantizando un entorno seguro (Safe Space) para menores, cumpliendo leyes de protección infantil (COPPA).
* **Alcance:** Creación de salas de chat, envío de texto/archivos, moderación automática, historial inmutable.
* **Actores:** Estudiante (Emisor/Receptor), Docente (Emisor/Receptor), IA Moderadora (Filtro), Admin (Auditor).

## 3. Contexto
* **Precondiciones:** 
  1. Relación existente entre Estudiante y Docente (matriculados en el mismo curso).
  2. Suscripción a canal WebSockets de Supabase Realtime abierta.
* **Disparador:** El usuario presiona "Enviar" en la ventana de chat.
* **Postcondiciones:** El mensaje se almacena cifrado, se escanea semánticamente, y si es seguro, se transmite al receptor vía Socket.

| Resultado / Campo | Tipo / Estado | Mensaje |
| :--- | :--- | :--- |

| `flagged` | BOOLEAN | Si fue retenido por el filtro de IA. |
| `403 Forbidden` | HTTP Error | "Conversación bloqueada" o "Sin permiso de envío". |

## 6. Flujo funcional
### Flujo principal (Envío Seguro)
1. El frontend emite el payload del mensaje.
2. NestJS valida (Zod) y comprueba que el remitente pertenece a la `conversation_id`.
3. (Filtro IA Nivel 1): El contenido pasa por una validación síncrona en milisegundos con un filtro Bloom/Regex de palabras prohibidas (Profanity Filter).
4. El mensaje se inserta en `chat_messages` (Postgres).
5. Se dispara un WebHook a Supabase Realtime para transmitir el mensaje a los clientes conectados a la sala.
6. (Filtro IA Nivel 2 Asíncrono): Un worker evalúa el mensaje con un modelo NLP (ej. OpenAI Moderation API) para detectar intenciones maliciosas (Grooming/Bullying).

### Flujos de excepción
* **FE-01: Mensaje Tóxico Detectado:** Si el modelo NLP devuelve un `flag = true` de toxicidad:
  1. Se actualiza el mensaje a `is_hidden = true`.
  2. Se envía un Webhook Realtime de revocación (el mensaje desaparece de la pantalla del receptor).
  3. Se inserta un reporte en `moderation_alerts` para que un Director lo revise.
* **FE-02: Fallo de conexión Socket:** El frontend guarda el mensaje con un icono de "reloj" (Pending) en IndexedDB y reintenta con Exponential Backoff cuando recupera conexión.

## 8. Reglas de negocio
* **RN-001 (Canales Estrictos):** Estudiantes no pueden abrir chats 1-a-1 con profesores que NO les estén dictando un curso en el periodo actual. (Prevención de acoso transversal).
* **RN-002 (Inmutabilidad):** Los mensajes no se pueden borrar físicamente (`DELETE`). La acción "Eliminar para todos" aplica un soft-delete (`deleted_at = NOW()`), pero el contenido original queda preservado en la DB por requerimientos de auditoría legal (Log retention policy).

## 9. Permisos y seguridad
* **Autenticación:** JWT.
* **Cifrado de Base de Datos:** Los mensajes usan TDE (Transparent Data Encryption) o cifrado de columna a nivel aplicación con `pgcrypto` para que incluso los DBAs no puedan leer conversaciones privadas sin llave (Privacy by Design).
* **RLS:**
  ```sql
  CREATE POLICY "Participantes leen sus chats" ON chat_messages
  FOR SELECT USING (
    EXISTS (SELECT 1 FROM conversation_participants cp 
            WHERE cp.conversation_id = chat_messages.conversation_id 
            AND cp.user_id = auth.uid())
  );
  ```

## 10. Persistencia
* **Tablas/Colecciones:** `conversations`, `conversation_participants`, `chat_messages`.
* **Rendimiento:** Particionamiento de la tabla `chat_messages` por meses (Partition by Range) para asegurar búsquedas rápidas cuando haya millones de mensajes en un tenant.

## 11. Integraciones
* **Realtime:** Supabase Realtime (WebSockets Channels).
* **IA de Moderación:** OpenAI Moderation API o GCP Perspective API.

## 12. Auditoría
* Los Directores del Tenant (rol `PRINCIPAL`) tienen acceso a un portal de "E-Discovery" donde pueden desencriptar y exportar hilos de chat SI Y SOLO SI hay un reporte formal de bullying. Toda auditoría de un director registra un log legal `ADMIN_AUDIT_LOG`.

## 13. Notificaciones
* Si el destinatario está offline (No hay subscripción al socket en los últimos 2 minutos), se encola un envío de notificación Push (FCM) o Email con el resumen de "Nuevos mensajes de Profesor X".

## 14. Criterios de aceptación (BDD)
* **CA-01: Moderación Inmediata**
  * *Given* que un alumno escribe lenguaje inapropiado
  * *When* envía el mensaje
  * *Then* la UI cambia el mensaje a "Mensaje bloqueado por incumplir normativas", no se envía al destinatario, y se alerta al director.
* **CA-02: Aislamiento Multitenant**
  * *Given* dos tenants distintos
  * *When* se intenta inyectar por API un mensaje hacia un `conversation_id` de otro colegio
  * *Then* PostgreSQL (RLS) bloquea la operación y retorna 403 o 404.

## 15. Casos de prueba relacionados
* `TC-RF011-01`: Simular tráfico de 1000 websockets concurrentes y medir latencia de entrega (T<100ms).
* `TC-RF011-02`: Bypass attempts de `sender_id` (asegurar que no se pueda hacer spoofing del ID de otro alumno).
