# RF-005: Otorgamiento Automático de Badges e Insignias

| Atributo | Detalle |

| **Módulo** | Gamificación / Economía Conductual |
| **Tipo** | Event-Driven (Procesamiento reactivo) |
| **Versión** | 1.0 |
| **Estado** | AUDITED (Enriquecido) |
| **Prioridad** | Media (Impacto masivo en Retención) |

## 2. Descripción funcional
* **Descripción:** Sistema de reglas basado en eventos que escucha el comportamiento del estudiante (completar lecciones, notas perfectas, rachas de conexión) y automáticamente le otorga Badges (insignias visuales) y Puntos de Experiencia (XP).
* **Objetivo:** Aumentar la retención y el engagement (Daily Active Users) aplicando mecánicas de gamificación.
* **Alcance:** Creación de catálogo de insignias (Admin), Motor de evaluación de reglas, UI de Perfil de Logros del estudiante.
* **Actores:** Sistema (Otorgante), Estudiante (Receptor), Admin (Configurador).

## 3. Contexto
* **Precondiciones:** 
  1. Catálogo de reglas y badges definido por el Tenant.
  2. Motor de eventos (Event Bus) escuchando acciones.
* **Disparador:** Un evento de dominio (ej. `LESSON_COMPLETED`, `COURSE_PASSED`, `STREAK_7_DAYS`).
* **Postcondiciones:** Un registro de logro asignado al perfil del estudiante y una animación visual disparada en el frontend.

## 4. Entradas
| Parámetro | Tipo | Obligatorio | Validaciones |
| :--- | :--- | :---: | :--- |
| `event_name` | VARCHAR | Sí | Registrado en el catálogo de eventos. |
| `payload` | JSONB | Sí | Contiene metadata (ej. `score`, `course_id`). |
| `user_id` | UUID | Sí | ID del usuario que generó la acción. |
| `tenant_id`| UUID | Sí | Aislamiento del catálogo de badges. |

## 5. Salidas
| Resultado / Campo | Tipo / Estado | Mensaje |
| :--- | :--- | :--- |
| `badge_awarded` | JSON | "Has ganado la insignia: Maestro de React!" |
| `xp_gained` | INT | +50 XP |
| `No Action` | Null | Si el evento no cumple la regla. |

## 6. Flujo funcional
### Flujo principal (Arquitectura Reactiva)
1. El estudiante finaliza un examen con nota perfecta.
2. El servicio de exámenes emite un evento interno (RabbitMQ / NestJS Event Emitter): `EXAM_PERFECT_SCORE`.
3. El `GamificationService` actúa como listener y procesa el evento asíncronamente.
4. El servicio consulta las `badge_rules` del `tenant_id` vinculadas a ese evento.
5. Evalúa las condiciones (ej. "Solo otorgar si es la primera vez").
6. Si cumple, inserta en la tabla `user_badges` e incrementa el XP total en el `student_profiles`.
7. El servicio publica un evento vía WebSockets a la conexión activa del usuario.
8. El frontend (React) intercepta el WebSocket y dispara un componente `Lottie` (fuegos artificiales) en pantalla completa y un Toast notification.

### Flujos alternativos
* **FA-01: Otorgamiento Manual:** Un profesor puede entrar al perfil del estudiante y otorgar una insignia "Blanda" (ej. "Liderazgo en clase") de manera manual saltándose el motor de reglas.

### Flujos de excepción
* **FE-01: Latencia de procesamiento:** Si hay un pico masivo de estudiantes terminando un curso al mismo tiempo, las insignias se procesan en cola (Queue). La animación visual llegará con un ligero retraso (Eventual Consistency), evitando saturar Postgres.

## 8. Reglas de negocio
* **RN-001 (Unicidad):** Si una insignia está marcada como `is_unique = true` (ej. "Graduado"), el motor verificará que el usuario no la posea antes de intentar insertarla (previniendo duplicados de UX).
* **RN-002 (Niveles):** El XP ganado recalcula automáticamente el `Nivel` del usuario. Si cruza un umbral (ej. 1000 XP -> Nivel 2), se emite un nuevo evento en cascada `LEVEL_UP`.

## 9. Permisos y seguridad
* **Políticas RLS:** 
  * Nadie puede forzar el insert en `user_badges` mediante la API cliente. El insert se realiza exclusivamente desde un backend Service Role (ignora RLS a nivel servicio) o vía Triggers de Postgres.

## 10. Persistencia
* **Tablas/Colecciones:** `user_badges`.
* **Transacciones:** Actualizar el XP del perfil de usuario (`UPDATE student_profiles SET total_xp = total_xp + X`) y otorgar el badge debe realizarse en una única transacción atómica en la DB para prevenir corrupciones matemáticas.

## 11. Integraciones
* **WebSockets (Realtime):** Supabase Realtime Channels.
* **Animaciones UI:** LottieFiles / Framer Motion para el componente de celebración.

## 12. Auditoría
* Histórico inmutable en `user_badges`. Si un estudiante hace trampa, un administrador puede revocar (borrado lógico) la insignia.

## 13. Notificaciones
* Se agrupan. Si un usuario gana 5 badges en un segundo (por acciones en cascada), se envía un solo correo resumen al final del día. En interfaz gráfica sí se muestran apiladas (Toast stack).

## 14. Criterios de aceptación (BDD)
* **CA-01: Disparo reactivo**
  * *Given* la regla "Completar primer módulo = Badge Pionero"
  * *When* el sistema guarda la lección final del módulo en la BD
  * *Then* se debe insertar asíncronamente la relación en `user_badges` sin afectar el tiempo de respuesta HTTP de la finalización de la lección.
* **CA-02: Celebración visual**
  * *Given* que el websocket recibe el payload de nueva insignia
  * *When* el estudiante está navegando en cualquier parte de la app
  * *Then* se pausa la navegación, se lanza una animación festiva y se reproduce un micro-sonido UI.
