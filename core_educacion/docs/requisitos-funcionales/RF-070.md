## 2. Descripción funcional
* **Descripción:** El mayor obstáculo para vender EDUCACION OS a un colegio es la migración de datos. "Tenemos 10 años de notas en Moodle y Excel, no queremos perderlas". Este RF es el "Puente del Bifröst". Un motor ETL que ingesta archivos CSV, backups de bases de datos antiguas (SQL) y conecta con APIs legacy. Extrae, limpia, normaliza, mapea y carga millones de registros históricos (Notas, Asistencia, Profesores) al esquema avanzado de EDUCACION OS.
* **Objetivo:** "Zero-to-Hero" en 24 horas. Lograr que un colegio pase de usar herramientas de los 90s a usar el sistema operativo educativo más avanzado del mundo sin perder un solo dato histórico, automatizando el Onboarding B2B.
* **Alcance:** Motor ETL en Cloud (Dataflow/Spark), Mapeador Visual (UI), Validación de Integridad Referencial.
* **Actores:** Administrador TI del Colegio, Ingeniero de Datos, Pipeline ETL.

## 3. Contexto
* **Precondiciones:** 
  1. Un colegio nuevo (Tenant) recién creado y vacío en la BD.
  2. Data cruda (Raw) subida a un Data Lake intermedio (Ej. Bucket S3 seguro).
* **Disparador:** El Administrador TI aprueba el archivo de "Mapeo" y lanza la importación.
* **Postcondiciones:** Población completa de todas las tablas core (Estudiantes, Notas, Históricos), gatillando el pre-cálculo del Gemelo Digital (RF-038).

## 6. Flujo funcional
### Flujo principal (Migración de Moodle)
1. El Colegio "San Ignacio" compra EDUCACION OS.
2. El TI del colegio exporta su base de Moodle completa (Archivos XML y SQL de 5GB) y los arrastra a la zona de "Data Drop" en la interfaz de onboarding.
3. El sistema sube los archivos a AWS S3 (Bucket de cuarentena).
4. Un proceso *Apache Spark* (o AWS Glue / GCP Dataflow) despierta.
5. (Extract) Lee la estructura legacy. (Transform) Limpia los datos, unifica formatos de fecha (`dd/mm/yyyy` -> `ISO 8601`), y resuelve IDs conflictivos. Genera los UUIDs nuevos preservando los `legacy_id` para referencias.
6. La UI le muestra al TI: *"Hemos encontrado 2,000 estudiantes y 150,000 notas. ¿Proceder?"*
7. (Load) Tras confirmar, el sistema usa *Bulk Inserts* (Copias masivas binarias `COPY` en Postgres) inyectando la data a la BD a 50,000 filas por segundo.
8. En 3 minutos, el colegio está operando en la nueva plataforma como si hubiese estado ahí toda la vida.

### Flujos alternativos
* **FA-01: Auto-Resolución de Duplicados (Deduplication):** Si un estudiante figura como "Luis Perez" en el sistema de pagos y como "L. Perez" en el sistema académico legacy, el motor ETL utiliza una librería NLP de *Fuzzy Matching* (Distancia de Levenshtein) para sugerir que son la misma persona y fusionar (Merge) sus registros automáticamente.

## 8. Reglas de negocio
* **RN-001 (Safe Rollback - Todo o Nada):** Si al inyectar las notas en el paso `Load`, el sistema falla en el registro 149,000, toda la migración completa debe revertirse (`ROLLBACK` transaccional) para no dejar la base de datos del colegio en un estado huérfano inconsistente.
* **RN-002 (Preservación PII y Borrado de Cuarentena):** Inmediatamente después de que el Job de Ingesta termina con éxito, los archivos crudos (Excel, SQL) que el colegio subió a S3 DEBEN ser purgados criptográficamente (Shredding) en máximo 24 horas, ya que constituyen una vulnerabilidad masiva de datos (PII).

## 9. Permisos y seguridad
* **Auditoría de Origen (Data Provenance):** Todo registro (Ej. Una nota) que nace a partir de una migración legacy recibe un flag booleano oculto `is_legacy_imported=true`. Esto asegura que los modelos de Inteligencia Artificial sepan que esos datos pueden contener sesgos de sistemas antiguos y pesen menos que los generados nativamente (RF-067).

## 10. Persistencia
* **Infraestructura ETL:** Cloud Storage (Data Lake Efímero) -> Apache Beam / Spark Cluster -> PostgreSQL (Capa Transaccional).

## 11. Integraciones
* **Conectores Nativos:** Integraciones directas (Airbyte, Fivetran o conectores propios) para conectarse mediante credenciales a bases de datos on-premise de los colegios (SQL Server antiguos) y extraer la data a través de un túnel VPN seguro.

## 14. Criterios de aceptación (BDD)
* **CA-01: Bulk Loading Performance**
  * *Given* un CSV de 1 Millón de filas de asistencias históricas
  * *When* el motor inicia la fase LOAD en PostgreSQL
  * *Then* debe utilizar el comando binario `COPY` o *Batch Inserts*, garantizando la inserción del millón de filas en menos de 180 segundos sin degradar el performance de otros colegios alojados en el clúster.
* **CA-02: Manejo de Tipos Estrictos**
  * *Given* un Excel antiguo donde la columna de "Fecha de Nacimiento" mezcla formatos (`01/02/2010`, `Feb 1st 10`, `N/A`)
  * *When* el transformador ETL procesa la columna
  * *Then* debe parsear inteligentemente a `ISO-8601` o convertir a `NULL` (con alerta en log), impidiendo que se inyecte texto corrupto en un campo de tipo `DATE` estricto en Postgres.

## 15. Casos de prueba relacionados
* `TC-RF070-01`: Migración "Chaos". Subir un volcado SQL malicioso de 2GB intentando inyectar `DROP TABLE` o caracteres NUL (0x00) en los textos. Verificar que la capa de transformación `Spark` sanitice y esterilice absolutamente cada bit antes de enviarlo al núcleo.
