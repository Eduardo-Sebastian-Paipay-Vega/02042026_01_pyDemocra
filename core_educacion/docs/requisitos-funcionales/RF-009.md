## 2. Descripción funcional
* **Descripción:** Tras procesar un cobro (RF-008), el sistema genera automáticamente un comprobante de pago con validez fiscal (Boleta o Factura Electrónica). Crea el PDF visual y el XML correspondiente exigido por entidades tributarias locales (Ej. SUNAT en Perú, DIAN en Colombia, SAT en México), apoyándose en APIs de Proveedores de Servicios Electrónicos (PSE/OSE).
* **Objetivo:** Cumplir con las normativas tributarias del país donde opera el Tenant de forma 100% automatizada (cero intervención contable manual).
* **Alcance:** Extracción de datos de facturación del cliente, generación de carga útil, comunicación con el OSE/PSE, y almacenamiento del CDR (Constancia de Recepción) y PDF.
* **Actores:** Comprador (Receptor), Sistema (Emisor), API OSE/SUNAT (Validador Fiscal).

## 3. Contexto
* **Precondiciones:** 
  1. Pago exitoso validado en la tabla `transactions`.
  2. Datos fiscales del cliente (RUC/DNI, Razón Social, Dirección) disponibles en `user_billing_profiles`.
  3. Tenant configurado con credenciales de facturación (Certificado Digital / API Key OSE).
* **Disparador:** Webhook de transacción completada (`status = 'SUCCESS'`) en el servicio de pagos.
* **Postcondiciones:** Documento tributario emitido, firmado, PDF generado y enviado por correo al cliente.

## 6. Flujo funcional
### Flujo principal (Facturación Síncrona / Asíncrona)
1. El `BillingService` recibe el evento de transacción exitosa.
2. Consulta el `user_billing_profile` del comprador.
3. Formatea el payload JSON estandarizado requerido por el intermediario (ej. Nubefact, NubeSFS, o Facturador Pro).
4. El intermediario aplica la firma digital y transmite a la Entidad Tributaria (SUNAT/SAT).
5. Retorna el XML firmado, el CDR y un PDF estandarizado.
6. El sistema guarda las URLs de estos documentos en el bucket interno (`invoice_files`) y actualiza la tabla `invoices`.
7. Dispara el correo electrónico con el PDF/XML adjunto al comprador.

### Flujos alternativos
* **FA-01: Anulaciones / Notas de Crédito:** Si se procesa un reembolso en Stripe, el sistema debe emitir automáticamente una Nota de Crédito Electrónica que afecte y anule al comprobante original.

### Flujos de excepción
* **FE-01: Caída del servicio tributario:** Si SUNAT/OSE está inoperativo (timeout), la factura se encola en una tabla `invoice_dead_letter_queue` o RabbitMQ con reintentos exponenciales (hasta por 3 días).

## 8. Reglas de negocio
* **RN-001 (Correlatividad Estricta):** Los números de comprobantes (`correlative`) no pueden tener vacíos (gaps). Si el comprobante falla en SUNAT, no se elimina; se anula formalmente para no romper la cadena numérica, y se emite el siguiente.
* **RN-002 (Impuestos Locales):** El cálculo de impuestos (ej. 18% IGV en Perú) es paramétrico y depende de la configuración fiscal `tenant_tax_settings`.

## 9. Permisos y seguridad
* **Políticas RLS:** Los clientes pueden ver sus propios comprobantes. Administradores del Tenant pueden ver todos los comprobantes generados por su empresa.
* **Seguridad de Firmas:** Las claves del certificado digital `.pfx` nunca se guardan en texto plano en la BD. Se inyectan como variables de entorno seguras (Secret Manager / Vault) o se confían al intermediario (OSE).

## 10. Persistencia
* **Tablas/Colecciones:** `invoices`, `tenant_tax_settings`.
* **Locking de Secuencias:** Para generar la numeración sin duplicidades (ej. dos pagos simultáneos de 2 clientes obteniendo el recibo "B001-40"), se debe utilizar una función SQL atómica de incremento (`FOR UPDATE` o secuencias Postgres `NEXTVAL('tenant_serie_seq')`).

## 11. Integraciones
* **APIs externas:** Nubefact, Migo, FacturadorPro (dependiendo de la localización de la escuela).

## 12. Auditoría
* Todas las repuestas de error de las entidades de gobierno (ej. "RUC inválido") quedan registradas en `invoice_audit_logs` para su revisión manual contable.

## 14. Criterios de aceptación (BDD)
* **CA-01: Auto-incremento sin Race Conditions**
  * *Given* que 50 pagos se procesan en el mismo segundo exacto
  * *When* el sistema genera el correlativo
  * *Then* ningún número de boleta debe repetirse (B001-01 al B001-50 generados atómicamente).
* **CA-02: Cuadre de montos**
  * *Given* un pago de 100.00 exactos con impuesto de 18%
  * *When* se genera el payload para el OSE
  * *Then* la base imponible (84.75) y el impuesto (15.25) deben sumar estrictamente 100.00 sin descuadres de redondeo al décimo (Round Half Up).
