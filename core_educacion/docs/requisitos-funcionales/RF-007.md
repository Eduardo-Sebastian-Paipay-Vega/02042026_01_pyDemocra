## 2. Descripción funcional
* **Descripción:** Un sistema de "Quests" que asigna a los estudiantes retos temporales (ej. "Completa 3 lecciones esta semana", "Obtén 20/20 en un quiz"). Al cumplir las condiciones antes de que expire el tiempo, reciben recompensas (Tokens internos, XP, o Badges especiales).
* **Objetivo:** Incrementar la frecuencia de uso de la plataforma (WAU - Weekly Active Users) dándole al estudiante objetivos a corto plazo más allá del currículo obligatorio.
* **Alcance:** Generación de retos (automáticos por cron o manuales por Admin), seguimiento de progreso del reto, reclamación de recompensa.
* **Actores:** Estudiante (Jugador), Admin/Sistema (Creador del Reto).

## 3. Contexto
* **Precondiciones:** 
  1. Motor de eventos (RF-005) operando.
  2. Misiones activas en la tabla `active_quests` para el tenant respectivo.
* **Disparador:** El cron scheduler (lunes 00:00) publica nuevos retos semanales.
* **Postcondiciones:** El estudiante cumple la condición, el estado de la misión pasa a `COMPLETED` y se transfieren las recompensas.

## 6. Flujo funcional
### Flujo principal (Cumplimiento de Misión)
1. El estudiante realiza una acción (ej. terminar una lección).
2. El sistema emite el evento `LESSON_FINISH`.
3. El `QuestTrackerService` verifica si el usuario tiene misiones activas que escuchen ese evento.
4. Encuentra "Completa 3 lecciones" (target=3).
5. Incrementa el contador en `user_quest_progress` de 1 a 2.
6. Si el contador llega a 3 (target alcanzado), marca la misión como `COMPLETED`.
7. Si la misión tiene auto-reclamar, transfiere los XP/Tokens de inmediato. Si no, notifica al UI para que el usuario presione el botón "Reclamar".

### Flujos alternativos
* **FA-01: Reclamación Manual (Efecto Lootbox):** Para aumentar la dopamina, la recompensa no se suma sola. El botón "Reclamar" brilla y, al hacer clic, hace una animación de apertura entregando los XP.

### Flujos de excepción
* **FE-01: Expiración Inminente:** Si el usuario completa el objetivo a las 23:59:59 y el worker de eventos procesa a las 00:00:01, el sistema usa el timestamp exacto del evento `created_at`, no el de procesamiento, para asegurar que el reto sea válido (Justicia del sistema).

## 8. Reglas de negocio
* **RN-001 (Ciclo de Vida):** Las misiones `WEEKLY` expiran irreversiblemente todos los domingos a las 23:59 hrs (hora del Tenant).
* **RN-002 (Prevención de Explotación):** Para misiones repetitivas ("Ver 3 videos"), el sistema implementa "debouncing". Ver la misma lección 3 veces seguidas no cuenta. Debe ser en IDs de lecciones distintas (regla paramétrica `unique_targets_only: true`).

## 9. Permisos y seguridad
* **Autenticación:** Requerida.
* **Autorización (RLS):**
  ```sql
  CREATE POLICY "Estudiantes ven sus misiones activas" ON user_quests 
  FOR SELECT USING (user_id = auth.uid() AND tenant_id = auth.jwt()->>'tenant_id');
  ```
* **Anti-cheat:** Los inserts de progreso son estricta potestad del backend service-role.

## 10. Persistencia
* **Tablas/Colecciones:** `quests`, `user_quests`.
* **Transacciones:** Cuando el estado cambia a `CLAIMED`, el crédito del reward y la actualización del estado deben ocurrir atómicamente (`BEGIN; ... COMMIT;`).

## 11. Integraciones
* **Motor de eventos interno:** NestJS `@OnEvent()`.

## 12. Auditoría
* Se guardan logs en `economy_ledger` cuando los retos entregan Tokens financieros para evitar inflación artificial en la economía de la app.

## 13. Notificaciones
* Notificación push (FCM) a las 48 horas antes de expirar: "Te falta 1 lección para completar el Reto Semanal!".

## 14. Criterios de aceptación (BDD)
* **CA-01: Validación de tiempo límite**
  * *Given* un reto que expiró hace 5 minutos
  * *When* el estudiante intenta presionar "Reclamar" usando una sesión abierta antigua (que aún no había refrescado el UI)
  * *Then* la API rechaza la transacción con un error 400 y actualiza el frontend mostrando el reto como expirado.
* **CA-02: Incremento atómico**
  * *Given* que el usuario completa dos lecciones casi simultáneamente (ej. múltiples pestañas)
  * *When* se lanzan dos eventos concurrentes
  * *Then* la base de datos debe usar un bloqueo de fila (`SELECT ... FOR UPDATE`) o una operación atómica (`current_count = current_count + 1`) para evitar Race Conditions.
