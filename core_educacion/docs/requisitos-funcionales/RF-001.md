## 2. Descripción funcional
* **Descripción:** El sistema permitirá a los docentes e instructores diseñar programas educativos estructurados en una jerarquía estricta: Curso > Módulo > Tema > Lección. Soportará versionado de currículos y publicación condicional.
* **Objetivo:** Estandarizar la creación de contenido académico asegurando que todos los recursos sigan un modelo pedagógico ordenado y escalable.
* **Alcance:** Creación, edición, reordenamiento (drag & drop) y publicación de estructuras curriculares. Afecta al motor principal de Educación.
* **Actores:** Administrador Tenant, Docente/Creador, Coordinador Académico.

## 3. Contexto
* **Precondiciones:** 
  1. El usuario posee el rol `CREATOR` o `ADMIN`.
  2. Contexto de tenant (`tenant_id`) estrictamente cargado en memoria (JWT).
  3. El Curso padre ya debe existir en estado `DRAFT` o `PUBLISHED`.
* **Disparador:** El docente hace clic en "Nuevo Módulo" dentro del Dashboard del Curso.
* **Postcondiciones:** La estructura curricular se almacena en la base de datos, el árbol de dependencias (DAG) se actualiza y la caché de lectura de estudiantes se invalida.

## 4. Entradas
| Parámetro | Tipo | Obligatorio | Validaciones |
| :--- | :--- | :---: | :--- |
| `course_id` | UUID | Sí | Debe existir y pertenecer al `tenant_id`. |
| `title` | VARCHAR(150) | Sí | Min 5, Max 150 caracteres. Sin inyección HTML. |
| `description` | TEXT | No | Max 500 caracteres. |
| `order_index` | INT | Sí | Número entero secuencial mayor a 0. |
| `status` | ENUM | Sí | Valores: `DRAFT`, `PUBLISHED`, `ARCHIVED`. |
| `metadata` | JSONB | No | Validar esquema JSON contra Zod (tags, horas estimadas). |

## 5. Salidas
| Resultado / Campo | Tipo / Estado | Mensaje |
| :--- | :--- | :--- |
| `module_id` | UUID | "Módulo creado exitosamente." |
| `tree_structure` | JSON | "Árbol curricular actualizado." |
| `403 Forbidden` | HTTP Error | "No tiene permisos para modificar este curso." |
| `409 Conflict` | HTTP Error | "Conflicto en el índice de ordenamiento." |

## 6. Flujo funcional
### Flujo principal
1. El usuario ingresa a la vista de edición del curso (`/cursos/[id]/builder`).
2. El frontend (React/Next.js) solicita el árbol curricular actual.
3. El usuario arrastra o añade un nuevo nodo (Módulo/Tema/Lección).
4. El frontend envía un payload estructurado vía API a NestJS.
5. El middleware de NestJS intercepta el JWT y extrae `tenant_id` y `user_id`.
6. El servicio backend valida el esquema (Zod/Class-Validator).
7. Supabase ejecuta la transacción garantizando integridad referencial.
8. El sistema devuelve el nuevo árbol estructurado.
9. El frontend renderiza el cambio sin recargar la página (Optimistic UI).

### Flujos alternativos
* **FA-01: Reordenamiento Masivo (Drag & Drop):** Si el usuario reordena, se envía un array de tuplas `[{id, new_order}]`. La DB actualiza en bloque dentro de una única transacción SQL usando `CASE`.

### Flujos de excepción
* **FE-01: Violación RLS:** Si un usuario intenta modificar un curso de otro tenant, Supabase rechaza a nivel Postgres (Error 42501). NestJS captura y lanza un `ForbiddenException` con un log de auditoría de seguridad grave.
* **FE-02: Colisión de Índices:** Si dos usuarios editan el mismo curso y generan colisión de `order_index`, la DB rechaza por constraint `UNIQUE(course_id, parent_id, order_index)`.

## 7. Objeto / Entidad (Modelo de Datos)
**Objeto Principal:** `curriculum_nodes` (Modelo de árbol por Adjacency List o Closure Table)

| Atributo | Tipo de Dato | Obligatorio | Restricciones | Descripción |
| :--- | :--- | :---: | :--- | :--- |
| `id` | UUID | Sí | PK, default `uuid_generate_v4()` | Identificador del nodo |
| `tenant_id` | UUID | Sí | FK a `tenants(id)`, Indexado | Aislamiento multitenant estricto |
| `course_id` | UUID | Sí | FK a `courses(id)` | Curso al que pertenece |
| `parent_id` | UUID | No | FK a `curriculum_nodes(id)` | Para la jerarquía (Módulo -> Tema -> Lección) |
| `node_type` | ENUM | Sí | `MODULE`, `TOPIC`, `LESSON` | Nivel jerárquico |
| `title` | VARCHAR(150) | Sí | - | Nombre visual del nodo |
| `order_index` | INT | Sí | `UNIQUE(parent_id, order_index)` | Orden en la lista |
| `status` | ENUM | Sí | default `DRAFT` | Control de publicación |
| `settings` | JSONB | No | - | Configuraciones extra (ej. es prerequisito) |

**Relaciones**
| Relación | Cardinalidad | Objeto Relacionado | Comportamiento |
| :--- | :---: | :--- | :--- |
| Pertenece a | N:1 | `tenants` | `ON DELETE CASCADE` |
| Pertenece a | N:1 | `courses` | `ON DELETE CASCADE` |
| Tiene hijo | 1:N | `curriculum_nodes` | Self-referencing (Padre-hijo) |
| Contiene | 1:1 | `content_blocks` | Relación con el material (Video, PDF, Quiz) |

## 8. Reglas de negocio
* **RN-001 (Estructural):** Una `LESSON` no puede tener hijos. Un `MODULE` solo puede ser hijo directo del Curso (no tener `parent_id`).
* **RN-002 (Inmutabilidad del Tenant):** Bajo ninguna circunstancia un nodo curricular puede transferirse de un `tenant_id` a otro.
* **RN-003 (Publicación en Cascada):** Si un `MODULE` pasa a estado `DRAFT`, todos sus temas y lecciones hijas quedan automáticamente inactivos para los estudiantes.

## 9. Permisos y seguridad
* **Autenticación:** Requerida (Supabase Auth / JWT en Header de NestJS).
* **Autorización:** 
  * Políticas RLS en la tabla `curriculum_nodes`: 
    ```sql
    CREATE POLICY "Tenant isolation" ON curriculum_nodes 
    FOR ALL USING (tenant_id = auth.jwt()->>'tenant_id');
    ```
* **Roles requeridos:** Rol `teacher` o `admin` validado a nivel JWT claim.

## 10. Persistencia
* **Tablas/Colecciones:** `curriculum_nodes`, `courses`.
* **Operaciones CRUD permitidas:** Insert, Update (Soft Delete mediante el cambio de `status` a `ARCHIVED` para no romper analíticas históricas).

## 11. Integraciones
* **APIs internas:** Interacción con el microservicio de **Progress Tracking** para inicializar los nodos de progreso del estudiante una vez publicado el módulo.
* **Caché:** Redis (Invalidación de caché de lectura en el endpoint `/api/v1/courses/:id/curriculum`).

## 12. Auditoría
* Cada mutación (Insert/Update) inserta un registro en la tabla `audit_logs`:
  `{ action: "CURRICULUM_UPDATED", entity_id: "[node_id]", user_id: "[user_uuid]", tenant_id: "[tenant_uuid]", timestamp: NOW(), diff: "[JSONB]" }`

## 13. Notificaciones
* Si el módulo es actualizado a estado `PUBLISHED` en un curso ya activo, se dispara un evento en RabbitMQ/Kafka a `Notification_Service` para avisar a los alumnos matriculados.

## 14. Criterios de aceptación (BDD)
* **CA-01: Aislamiento Tenant**
  * *Given* que el usuario está en el tenant A
  * *When* intenta agregar una lección a un módulo del tenant B (mediante spoofing de IDs en el request)
  * *Then* la base de datos rechaza la operación por RLS y retorna un error 403 o Entity Not Found.
* **CA-02: Jerarquía Estricta**
  * *Given* que un usuario tiene un nodo de tipo `LESSON`
  * *When* intenta añadirle un nodo hijo de tipo `TOPIC`
  * *Then* la validación de negocio (NestJS interceptor/DTO) bloquea la petición y lanza un `400 Bad Request`.
* **CA-03: Optimistic UI**
  * *Given* un arrastre (Drag&Drop) en el frontend
  * *When* se suelta el elemento
  * *Then* el UI se actualiza inmediatamente mostrando un Skeleton y el cambio se consolida cuando la API retorna 200 OK.
