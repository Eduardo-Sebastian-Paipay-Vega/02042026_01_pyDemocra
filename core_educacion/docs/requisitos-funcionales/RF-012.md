## 2. Descripción funcional
* **Descripción:** Hub unificado (Campanita superior) que agrega todas las notificaciones push de la plataforma: nuevas notas, recordatorios de pagos, misiones cumplidas, y mensajes directos. Incorpora categorización, marcaje de "leído" y limpieza automática (TTL).
* **Objetivo:** Prevenir la sobrecarga informativa (Notification Fatigue) al usuario, agrupando de manera inteligente alertas del sistema bajo un mismo panel.
* **Alcance:** Menú desplegable en la barra de navegación. Almacenamiento e ingesta de notificaciones.
* **Actores:** Cualquier Usuario autenticado (Receptor).

## 3. Contexto
* **Precondiciones:** 
  1. Usuario logueado (JWT válido).
  2. Servicios core emitiendo eventos al Notification Bus.
* **Disparador:** Generación de un evento en el sistema (ej. Docente publica una nota).
* **Postcondiciones:** Icono de campana muestra badge rojo (contador `unread_count`). Se persiste el aviso en `user_notifications`.

## 6. Flujo funcional
### Flujo principal (Lectura y Marcaje)
1. El sistema backend (mediante eventos RabbitMQ/Kafka) inserta un nuevo aviso en la BD y despacha un Websocket `NOTIFICATION_NEW` al frontend activo.
2. El contador visual (badge) incrementa reactivamente (+1).
3. El usuario hace clic en el ícono de la campana.
4. Se despliega el `<NotificationMenu />` listando las 10 últimas alertas.
5. El componente frontend ejecuta un background fetch (`PATCH /api/v1/notifications/mark-read`) enviando los IDs de las notificaciones que fueron intersectadas en el viewport (IntersectionObserver) para marcarlas como leídas silenciosamente.

### Flujos alternativos
* **FA-01: Agrupación Automática:** Si un profesor califica 5 tareas seguidas, el sistema en vez de mostrar 5 notificaciones de "Tarea calificada", fusiona (debounces) en una sola: "Tienes 5 tareas calificadas recientemente".

### Flujos de excepción
* **FE-01: Caída de la base de datos:** Si la consulta del inbox falla, el menú de notificaciones entra en `Offline Fallback` (Fallback UI: "No se pudieron cargar las alertas") pero no rompe el flujo principal de la app.

## 8. Reglas de negocio
* **RN-001 (Retention Policy):** Las notificaciones no son eternas (para cuidar costos de Storage). Una vez superados los 30 días, un CronJob ejecuta un Hard Delete sobre toda notificación con `is_read = true` y de tipo no crítico.
* **RN-002 (Preferencias del usuario):** El usuario puede desactivar tipos de alertas (ej. apagar alertas "SOCIALES") en su panel de configuración `user_preferences`. El Notification Bus evaluará este JSON antes de insertar el aviso.

## 9. Permisos y seguridad
* **Políticas RLS:** 
  ```sql
  CREATE POLICY "Lectura de Inbox Propio" ON user_notifications 
  FOR SELECT USING (user_id = auth.uid());
  
  CREATE POLICY "Actualizar a Leído" ON user_notifications 
  FOR UPDATE USING (user_id = auth.uid()) WITH CHECK (is_read = true); 
  -- (Evita que inyecten un payload distinto en el UPDATE)
  ```

## 10. Persistencia
* **Tablas/Colecciones:** `user_notifications`.
* **Rendimiento (Indexación):** Índice compuesto en Postgres `(user_id, is_read, created_at)` para que la consulta del badge (count) sea resuelta en < 5ms.

## 14. Criterios de aceptación (BDD)
* **CA-01: Auto-marcaje por intersección (Lectura inteligente)**
  * *Given* que el usuario tiene 10 notificaciones sin leer, y abre el panel
  * *When* hace scroll y solo ve visualmente las primeras 5
  * *Then* el sistema solo debe mandar un PATCH para marcar como leídas las 5 que entraron al Viewport, reduciendo el contador a 5 (no a 0 de golpe).
* **CA-02: Filtro de Preferencias**
  * *Given* un estudiante con preferencias `notify_social: false`
  * *When* un compañero le envía una solicitud de amistad
  * *Then* la notificación es dropeada en memoria por el Bus y jamás llega a la base de datos `user_notifications`.
