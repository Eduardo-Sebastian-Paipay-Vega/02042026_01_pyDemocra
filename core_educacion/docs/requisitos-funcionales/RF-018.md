# RF-018: Sincronización ERP Contable (SAP, Oracle, QuickBooks)

## 1. Identificación
| Atributo | Detalle |

| **Código** | RF-018 |
| **Nombre** | Sincronización ERP Contable (SAP, Oracle, QuickBooks) |
| **Módulo** | Integraciones / Facturación |
| **Tipo** | Data Pipeline (ETL / Event-Driven Sync) |
| **Versión** | 1.0 |
| **Estado** | AUDITED (Enriquecido) |
| **Prioridad** | Media (Esencial para Colegios Grandes / B2B Enterprise) |

## 2. Descripción funcional
* **Descripción:** Sistema de puenteo de datos que envía las operaciones financieras de la escuela (Matrículas, Pagos Recibidos, Notas de Crédito, Generación de Facturas) a su software de contabilidad empresarial (ERP) de manera bidireccional o unidireccional.
* **Objetivo:** Prevenir el doble tipeo (Double-entry) en la oficina contable. Las cobranzas realizadas en la plataforma deben cuadrar mágicamente en los libros diarios del colegio en su ERP principal.
* **Alcance:** Transformación de datos al esquema del ERP, cola de transmisión, manejo de errores y conciliación de saldos.
* **Actores:** Sistema (Productor), ERP Externo (Consumidor), Administrador Financiero (Auditor).

## 3. Contexto
* **Precondiciones:** 
  1. Tenant con plan `ENTERPRISE`.
  2. Credenciales del ERP configuradas (API Keys / OAuth2) en `tenant_erp_settings`.
* **Disparador:** Generación de un evento contable crítico (ej. `INVOICE_GENERATED`).
* **Postcondiciones:** Asiento contable registrado exitosamente en el ERP externo.

## 6. Flujo funcional
### Flujo principal (Sincronización Event-Driven)
1. Un alumno paga su cuota (RF-008). El sistema emite la factura (RF-009).
2. El Notification Bus despacha un evento `FINANCIAL_TX_COMPLETED`.
3. El módulo `ErpSyncWorker` escucha el evento.
4. Identifica qué adaptador usar según el `tenant_erp_settings` (ej. Adaptador de QuickBooks).
5. Convierte el JSON interno al formato estricto que exige el ERP (Data Mapping/Transformation).
6. Envía el POST a la API de QuickBooks (ej. Crear Customer si no existe, luego crear Payment vinculado a Invoice).
7. Guarda el ID externo devuelto en la tabla `erp_sync_logs` y actualiza la fila de origen indicando que ya fue conciliada.

### Flujos de excepción
* **FE-01: Caída del ERP / API Rate Limit:** Los ERPs (especialmente SAP o APIs antiguas) son frágiles o tienen estrictos Rate Limits. El Worker asume un patrón de diseño **Dead Letter Queue (DLQ)**. Si la llamada falla, se encola con *Exponential Backoff* (reintento a los 5 min, luego 30 min, luego 2h).
* **FE-02: Errores Lógicos (400 Bad Request):** Si el ERP dice "Código contable no existe", no se reintenta (es inútil). Se marca como `FAILED` y se alerta en el Dashboard del contador para revisión manual.

## 8. Reglas de negocio
* **RN-001 (Mapping de Cuentas Contables):** Cada curso o producto en nuestra BD debe tener un campo `accounting_ledger_code` (ej. "7010-Matriculas"). Al sincronizar, el ERP exige este código para saber a qué libro diario enviar el ingreso.
* **RN-002 (Doble Sincronización Prevenida):** Una transacción jamás debe sincronizarse dos veces para evitar ingresos duplicados irreales en los libros de la empresa.

## 9. Permisos y seguridad
* **Cifrado de Credenciales:** Las API Keys o tokens OAuth de SAP/QuickBooks son altamente sensibles (permiten robar fondos empresariales). Se almacenan en BD con encriptación AES-256 GCM o en un Secret Manager (GCP/AWS).

## 10. Persistencia
* **Tablas/Colecciones:** `erp_sync_logs`, `tenant_erp_settings`.
* **Idempotencia:** La tabla de logs usa un Constraint `UNIQUE (tenant_id, entity_type, entity_id)` para asegurar que una misma factura no pueda tener más de un registro de sincronización exitoso.

## 11. Integraciones
* **Arquitectura de Adaptadores:** Uso de Patrón *Adapter/Strategy* en NestJS para soportar N proveedores (QuickBooks API, SAP B1 Service Layer, Xero API) sin manchar la lógica de negocio core.

## 12. Auditoría
* Panel de "Salud de Integración" en el dashboard de la escuela, mostrando cuántos registros están en `FAILED` esperando corrección humana (ej. mapeo de cuentas incorrecto).

## 13. Notificaciones
* Si ocurren > 10 fallos de sincronización seguidos, se envía un correo urgente al Administrador Financiero.

## 14. Criterios de aceptación (BDD)
* **CA-01: Resiliencia ante fallas de Red (DLQ)**
  * *Given* que el servidor de SAP del colegio está caído por mantenimiento
  * *When* ocurren 50 pagos en la plataforma
  * *Then* el sistema encola los 50 eventos y realiza reintentos progresivos, logrando la sincronización exitosa horas después cuando SAP levanta, sin perder ni un solo céntimo en los libros.
* **CA-02: Garantía Anti-Duplicados**
  * *Given* que un pago ya tiene status `SYNCED`
  * *When* un administrador fuerza un re-envío desde el UI por error
  * *Then* la API rechaza la petición indicando "Transacción ya conciliada externamente".
