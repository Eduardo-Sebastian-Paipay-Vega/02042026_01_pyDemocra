## 2. Descripción funcional
* **Descripción:** Implementación de Aprendizaje Federado (Federated Learning). Permite a la plataforma central mejorar sus modelos de IA (ej. predicción de deserción, corrección de ensayos) aprendiendo de los datos de todos los colegios de la red B2B, **sin que los datos crudos (PII) salgan nunca del servidor o base de datos de cada colegio**.
* **Objetivo:** Superar la objeción B2B número 1: *"No queremos que los datos de nuestros alumnos se usen para entrenar la IA que usan otros colegios"*. Garantiza privacidad matemática, construyendo un "Modelo Global Inteligente" con "Datos Locales Seguros".
* **Alcance:** Entrenamiento de modelos Edge/Local, agregación segura de pesos (Secure Aggregation), distribución de modelo actualizado.
* **Actores:** Tenant/Colegio (Nodo Local), Servidor Central EDUCACION OS (Agregador).

## 3. Contexto
* **Precondiciones:** 
  1. Múltiples tenants B2B activos recolectando datos (RF-025).
  2. Consentimiento contractual B2B para "Mejora Anónima del Algoritmo".
* **Disparador:** Ventana de mantenimiento mensual (Ej. Día 1 de cada mes).
* **Postcondiciones:** Modelo Global actualizado y re-distribuido a todos los colegios.

## 6. Flujo funcional
### Flujo principal (Federated Averaging - FedAvg)
1. **Distribución:** El servidor central envía el Modelo Global base (pesos neutrales) a todos los Tenants (ej. Nodos de colegio aislados lógicamente o físicamente).
2. **Entrenamiento Local:** Cada colegio ejecuta un worker local (en su partición segura) que entrena el modelo *solo* con los datos de sus alumnos (ej. 100,000 registros). 
3. **Envío de Gradientes:** El colegio NO envía los nombres ni las notas de los alumnos. Solo envía a la nube un archivo matemático (Tensores/Gradientes) con lo que el modelo "aprendió".
4. **Agregación Central:** El servidor de EDUCACION OS recibe los tensores de 50 colegios. Usa el algoritmo *Federated Averaging (FedAvg)* para promediar los pesos.
5. **Actualización:** El servidor genera un Nuevo Modelo Global más inteligente y lo envía de vuelta a los 50 colegios.

### Flujos de excepción
* **FE-01: Data Poisoning (Ataque de Envenenamiento):** Si un colegio malicioso (o hackeado) altera sus notas intencionalmente para destruir el modelo global y envía tensores venenosos. El servidor central debe usar una "Byzantine-Robust Aggregation" (Krum o Median) que detecta gradientes estadísticamente anómalos y rechaza el envío de ese colegio.

## 8. Reglas de negocio
* **RN-001 (Zero-Knowledge):** Es un requisito contractual que la arquitectura backend impida, a nivel de red, que la instancia "Agregadora" central pueda hacer queries tipo `SELECT` a la tabla `student_profiles` de un tenant. 
* **RN-002 (Opt-out):** Cualquier colegio puede ir a Settings y presionar "Desactivar Aprendizaje Federado". Seguirán recibiendo el Modelo Global, pero su nodo local dejará de consumir CPU para entrenar gradientes.

## 9. Permisos y seguridad
* **Differential Privacy:** Además del Federated Learning, el worker local aplica *Privacidad Diferencial* (agregando "Ruido" matemático a los gradientes) antes de enviarlos al servidor. Esto garantiza matemáticamente que sea imposible hacer "Ingeniería Inversa" a los pesos para averiguar si un alumno en particular pertenecía al dataset (Defensa contra Membership Inference Attacks).

## 10. Persistencia
* **Tablas/Colecciones:** Almacenamiento de pesos de modelos en GCS (Google Cloud Storage) u S3, referenciados en BD.
* **Formatos ML:** Uso de ONNX o Safetensors (HuggingFace) por seguridad, ya que los archivos Pickle (`.pkl`) de Python pueden contener malware/RCE.

## 11. Integraciones
* **Framework ML:** `TensorFlow Federated` (TFF) o `Flower` (Framework open-source de Federated Learning).

## 12. Auditoría
* Para cumplir con auditorías GDPR, el sistema puede demostrar mediante logs de red que ningún byte de texto plano (nombres, notas) viajó por HTTP(S) hacia el agregador central, solo matrices flotantes.

## 13. Notificaciones
* Aviso administrativo a los colegios: "El modelo de Inteligencia Artificial ha mejorado un 5% este mes gracias a la red distribuida".

## 14. Criterios de aceptación (BDD)
* **CA-01: Protección de Seguridad de Formato (SafeTensors)**
  * *Given* que el servidor recibe los pesos de un tenant
  * *When* el archivo es un Pickle (`.pkl`) inyectado con código malicioso
  * *Then* la API de agregación debe rechazarlo en el Gateway exigiendo el formato inerte `.safetensors`, protegiendo el clúster central de ejecución remota (RCE).
* **CA-02: Agregación Bizantina (Byzantine Fault Tolerance)**
  * *Given* 10 colegios, donde 1 envía gradientes destructivos (Poisoning)
  * *When* el servidor procesa la ronda FedAvg
  * *Then* el algoritmo descarta los gradientes que superan 3 desviaciones estándar (Outliers) y promedia solo los 9 colegios honestos.
