## 2. Descripción funcional
* **Descripción:** EDUCACION OS no es solo un LMS, es el cerebro operativo del colegio. Este requisito maneja el dinero real (Fiat) de la institución: Cobro de pensiones escolares (colegiaturas), matrículas, integraciones con pasarelas de pago (Stripe/PayPal), generación de Facturas Electrónicas (para autoridades tributarias del país) y gestión de morosidad.
* **Objetivo:** Eliminar la necesidad de que el colegio pague SAP o software contable de terceros. Automatizar los recordatorios de pago a padres y generar bloqueos de sistema por morosidad (si las leyes del país lo permiten).
* **Alcance:** Pasarela de Pagos (Payment Gateway), Generador de PDFs (Facturas), Motor XML (Tributario), Motor de Morosidad.
* **Actores:** Padre de Familia (Pagador), Administrador Financiero (Cobrador), Pasarela de Pago (Liquidador).

## 3. Contexto
* **Precondiciones:** 
  1. Portal de Padres (RF-033) habilitado.
  2. Credenciales de la pasarela de pagos configuradas (Stripe API Keys) en el Tenant.
* **Disparador:** Llega el 1er día del mes (Cron Job).
* **Postcondiciones:** Generación masiva de obligaciones de pago (Deudas) para todos los alumnos matriculados.

## 6. Flujo funcional
### Flujo principal (Cobro y Facturación)
1. El motor de Batch Processing (BullMQ) se despierta el 1 de Marzo. Emite 1,000 obligaciones de pago de "Pensión Marzo" por $200 cada una.
2. Los padres reciben una notificación push: "Nueva obligación de pago disponible".
3. El Padre entra a EDUCACION OS, hace clic en "Pagar". Se abre un Modal de Stripe. Ingresa su tarjeta Visa.
4. Stripe procesa el cargo y dispara un **Webhook** al servidor de EDUCACION OS: `payment_intent.succeeded`.
5. El sistema marca la obligación como `PAID` (Pagada).
6. Inmediatamente, el servicio de Facturación Electrónica empaqueta la transacción en un archivo XML (cumpliendo estándares de la SUNAT/DIAN/SAT) y la envía al Gobierno.
7. Se genera un archivo PDF con la factura, que queda depositado en la "Bóveda Financiera" del Padre.

### Flujos de excepción
* **FE-01: Morosidad (Late Fees):** Pasa la fecha de vencimiento (`due_date`) y el padre no ha pagado. El Cron Job detecta la mora, aplica automáticamente un 5% de recargo por pago tardío y envía un correo rojo (Urgent). El sistema puede (según configuración legal del Tenant) restringir el acceso a la descarga de libretas de notas hasta regularizar la deuda.

## 8. Reglas de negocio
* **RN-001 (Precisión Decimal Absoluta):** Todas las tablas que manejan dinero fiat DEBEN usar tipos de datos numéricos exactos (Ej. `DECIMAL(10,2)` en Postgres) y nunca `FLOAT` o `DOUBLE`, para evitar errores matemáticos de coma flotante que resulten en descuadres contables de centavos ($199.99999).
* **RN-002 (Idempotencia de Webhooks):** Si Stripe falla y envía el evento de "Pago Exitoso" dos veces, el endpoint del Webhook debe usar el `Stripe-Event-Id` como llave de Idempotencia. Ignora el segundo intento para no crear facturas duplicadas (Protección contra Race Conditions).

## 9. Permisos y seguridad
* **PCI-DSS Compliance:** EDUCACION OS nunca, bajo ninguna circunstancia, toca, lee o almacena el número de tarjeta de crédito original (PAN) del cliente. Toda captura de tarjeta se hace mediante `Stripe Elements` o iframes tokenizados. El sistema solo guarda el token opaco (`tok_1234`).

## 10. Persistencia
* **Tablas/Colecciones:** Base de datos Relacional (PostgreSQL). Las colas de Webhooks entrantes deben persistirse en colas durables (RabbitMQ / BullMQ) para garantizar que ningún pago se pierda si la DB principal se reinicia durante la notificación bancaria.

## 11. Integraciones
* **Pasarelas de Pago:** Stripe API, MercadoPago API (Latinoamérica).
* **Entidades Tributarias:** APIs de SUNAT, SAT, DIAN (Facturación electrónica B2G).

## 12. Auditoría
* Módulo "Arqueo de Caja" (Reconciliation). A fin de mes, el sistema compara todos los pagos marcados como `PAID` en su Base de Datos contra el reporte bancario (CSV del Banco). Si hay un pago faltante (Descuadre), emite una Alerta a Contabilidad.

## 13. Notificaciones
* Aviso Push / Email: "Tu pago de $200 ha sido procesado exitosamente. Tu factura electrónica #F-1029 está disponible".

## 14. Criterios de aceptación (BDD)
* **CA-01: Idempotencia de Liquidación**
  * *Given* una factura pendiente
  * *When* se envían tres peticiones POST simultáneas simulando webhooks de "Pago Completado"
  * *Then* la base de datos debe actualizar el estado de la factura exactamente una vez y registrar el pago en la contabilidad exactamente una vez, retornando HTTP 200 en las tres pero sin duplicar dinero.
* **CA-02: Cálculos Financieros sin Pérdida**
  * *Given* una pensión de $100 con un impuesto de 18% (IVA) y un descuento del 15%
  * *When* el motor calcula el total final
  * *Then* debe aplicar redondeo bancario (Banker's rounding) estricto y los totales deben cuadrar hasta el último centavo sin pérdida por flotantes.

## 15. Casos de prueba relacionados
* `TC-RF059-01`: Simular fallas en la red (Network Drops) justo en el momento en que la base de datos intenta commitear la transacción pagada. Asegurar que el sistema de Event Sourcing marque el pago para revisión manual (Dead Letter Queue) en vez de perderlo silenciosamente.
