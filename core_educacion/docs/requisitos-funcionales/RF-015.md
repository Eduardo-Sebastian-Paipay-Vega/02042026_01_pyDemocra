## 2. Descripción funcional
* **Descripción:** Panel de visualización de datos (Dashboard) extremadamente visual que unifica múltiples dimensiones de un estudiante: Rendimiento académico (Notas), Comportamiento, Asistencia, Gamificación (XP/Badges), Tiempo de conexión, e Indicadores de salud mental detectados.
* **Objetivo:** Otorgar a Directores, Tutores Psicológicos y Docentes una "Radiografía" integral del estudiante en un solo lugar, permitiendo la toma de decisiones basada en datos (Data-driven intervention).
* **Alcance:** Interfaz de lectura intensiva. Gráficos interactivos (Echarts/Recharts), radares de competencias y cruce de datos de todos los submódulos.
* **Actores:** Docente, Psicólogo, Director, Padre de Familia (Versión lite).

## 3. Contexto
* **Precondiciones:** 
  1. Base de datos con históricos suficientes de notas, interacciones y asistencias.
  2. Tablas analíticas (Data Warehouse interno) procesadas.
* **Disparador:** Acceder a la ruta `/estudiantes/[uuid]/perfil-360`.
* **Postcondiciones:** Visualización de métricas en menos de <800ms.

| `radar_competencies`| JSON | Array de competencias [Pensamiento Crítico, Liderazgo, etc.]. |
| `engagement_score` | INT | (0-100) Indicador calculado basado en login y actividad (RF-016 base). |

## 6. Flujo funcional
### Flujo principal (Lectura de Telemetría)
1. El usuario busca un alumno y abre su Perfil 360.
2. El frontend de React inicia llamadas concurrentes (Promise.all) usando `React Query / SWR` a múltiples micro-endpoints analíticos (ej. `/api/v1/students/:id/academic`, `/api/v1/students/:id/behavior`).
3. El API Gateway (NestJS) rutea y junta la información.
4. Para evitar colapsar la DB con sumatorias masivas en caliente (Ej. Contar miles de clics de video), se consulta una base de datos OLAP (ClickHouse) o se leen Vistas Materializadas en Postgres.
5. Los datos se envían al frontend, que renderiza Gráficos de Radar (Spider web), Curvas de tendencia (Line charts) y un Semáforo de riesgo general.

### Flujos de excepción
* **FE-01: Datos Insuficientes (Cold Start):** Si el estudiante es completamente nuevo, los gráficos de radar o tendencias no tienen qué mostrar. En lugar de errores matemáticos (NaN o división por cero), la interfaz maneja graciosamente "Empty States" pidiendo tiempo para recolectar datos.

## 7. Objeto / Entidad (Modelo de Datos)
**Objeto Principal:** Datos agregados, no una tabla relacional directa. La tabla principal de consolidación analítica es `student_daily_aggregates` (Data Mart).

**Relaciones**
Este Data Mart agrupa métricas transversales de los módulos de Gamificación, Evaluación y Videos.

## 8. Reglas de negocio
* **RN-001 (Indexación B2B vs B2C):** La vista del Padre (B2C) censura o enmascara datos delicados (ej. Apuntes privados psicológicos) que solo están disponibles en la vista del Director/Psicólogo (B2B).
* **RN-002 (Cálculo del Engagement):** El `engagement_score` se calcula como: (30% asistencia + 40% entregas a tiempo + 30% participación en chats/foros).

## 9. Permisos y seguridad
* **Privacidad COPPA / FERPA:** Estricta observancia del control de accesos (IAM). Solo el rol `TUTOR_LEGAL` asignado específicamente a ese UUID puede ver los datos del estudiante, junto con profesores que actualmente dictan clases a dicho alumno.
* **RLS (Postgres):** Las consultas de analíticas usan uniones (`JOIN`) con la tabla de `enrollments` para asegurar autorización.

## 10. Persistencia
* **Tablas/Colecciones:** Operamos sobre un entorno ELT/ETL interno. Un Cronjob en DB (o Dataform) corre cada noche a las 3:00 AM para consolidar las tablas relacionales pesadas hacia `student_daily_aggregates` y optimizar la lectura diurna del Dashboard.

## 11. Integraciones
* **Gráficos UI:** Apache ECharts o Recharts.
* **Analítica Externa (Opcional):** Posible federación de datos a Google BigQuery o AWS Redshift si la institución es muy masiva.

## 12. Auditoría
* Se auditan (loguean) los accesos a los historiales de salud mental/disciplinarios del estudiante por razones de Privacidad y Ética (Quién vió el perfil de quién y cuándo).

## 14. Criterios de aceptación (BDD)
* **CA-01: Rendimiento (Sub-second response)**
  * *Given* una base de datos con historiales de 3 años de un alumno
  * *When* el Director carga el Perfil 360
  * *Then* la respuesta de la API no debe tardar más de 800ms, forzando la lectura desde vistas pre-calculadas en lugar de hacer SUM() y GROUP BY en caliente sobre millones de logs.
* **CA-02: Máscara de Privacidad**
  * *Given* que un profesor de Matemáticas carga el perfil 360
  * *When* intenta acceder a la pestaña "Notas Psicológicas"
  * *Then* la pestaña no debe existir en su payload ni interfaz, garantizando aislamiento de roles inter-institución.
