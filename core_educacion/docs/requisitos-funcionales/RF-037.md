## 2. Descripción funcional
* **Descripción:** EDUCACION OS no depende de un solo "Gran LLM" que responde todo (y se equivoca por falta de foco). Implementa una arquitectura de *Agentic Swarm* (Agentes Múltiples). Cuando el sistema enfrenta un problema complejo, un "Agente Orquestador" divide la tarea y llama a Sub-Agentes especialistas (ej. Agente Matemático, Agente Psicólogo, Agente Revisor de Código). Estos agentes debaten entre sí, corrigen sus errores y devuelven una respuesta final validada.
* **Objetivo:** Reducir drásticamente las alucinaciones de la IA. Aumentar la capacidad de razonamiento lógico (Chain of Thought / ReAct) para tareas complejas como calificar ensayos de Filosofía o resolver problemas de Física Cuántica.
* **Alcance:** Orquestador (Router), Agentes Especialistas (Tools), Sistema de Memoria Compartida.
* **Actores:** IA Orquestadora, IA Especialistas (Workers).

## 3. Contexto
* **Precondiciones:** 
  1. Integración con frameworks multi-agente (LangChain LangGraph o AutoGen).
  2. APIs de LLM potentes (GPT-4o, Claude 3.5 Sonnet, o Llama-3-70b).
* **Disparador:** Un usuario lanza un prompt de alta complejidad (ej. "Revisa esta tesis de 50 páginas y encuentra las contradicciones argumentativas").
* **Postcondiciones:** Resultado consensuado por el enjambre tras N iteraciones.

## 6. Flujo funcional
### Flujo principal (Debate Multi-Agente)
1. El docente pide: "Genera un examen de Física sobre Dinámica, asegúrate que ninguna pregunta tenga respuesta negativa, y que cubra el sílabo".
2. El **Agente Orquestador (Router)** recibe el prompt. Entiende que necesita 3 especialistas: `CurriculumAgent` (Conoce el sílabo), `PhysicsAgent` (Crea el problema), y `MathValidatorAgent` (Resuelve la ecuación para validar).
3. El `PhysicsAgent` genera 10 problemas.
4. Pasa el borrador al `MathValidatorAgent`. Este descubre que el problema 4 da un resultado de masa negativa (Error físico).
5. El Validator envía feedback al Physics: "Corrige el problema 4, la masa no puede ser negativa".
6. El PhysicsAgent regenera el problema 4. 
7. El Orquestador junta todo, lo formatea y se lo entrega al docente en la UI.
8. Todo esto sucede en background en ~15 segundos.

### Flujos de excepción
* **FE-01: Disputa Irresoluble (Infinite Loop):** Si el Agente A y el Agente B entran en un bucle discutiendo infinitamente, al llegar a la iteración 10 (`max_iterations`), el Orquestador corta el proceso, emite un "Consenso Parcial" y alerta al humano: "Revisión manual requerida en la Pregunta 4".

## 8. Reglas de negocio
* **RN-001 (Model Routing):** Para optimizar costos (LLM Routing), los sub-agentes fáciles (ej. `FormatAgent` que solo hace Markdown) usan modelos baratos (GPT-4o-mini o Llama-3-8b). Solo el `MathValidatorAgent` o el `Orquestador` usan modelos caros y pesados (Claude 3.5 Sonnet / GPT-4).
* **RN-002 (Caja de Arena - Sandboxing):** Si un sub-agente (ej. `CodeExecutorAgent`) necesita ejecutar código Python para resolver una ecuación, debe hacerlo en un contenedor Docker efímero y ultra-seguro (Firecracker microVM) sin acceso a internet ni a la red interna de EDUCACION OS.

## 9. Permisos y seguridad
* **Tool Access Control:** No todos los agentes tienen acceso a todas las herramientas (Tools). El `WriterAgent` no tiene permisos para ejecutar queries SQL a la base de datos. Solo el `DatabaseAgent` (Con permisos Read-Only restringidos por Tenant) puede hacerlo.

## 10. Persistencia
* **Tablas/Colecciones:** Almacenamiento de logs de trazas en Elasticsearch / MongoDB para visualización del "Pensamiento de la IA".

## 11. Integraciones
* **Framework Multi-Agent:** LangGraph (TypeScript/Python) o Microsoft AutoGen.
* **Ejecución de Código Efímera:** Integración con E2B (e2b.dev) o un clúster de Kubernetes con gVisor para sandboxing de Python.

## 12. Auditoría
* La UI debe permitir al usuario expandir un acordeón llamado "Ver el razonamiento de la IA" para leer el log de cómo los agentes llegaron a esa respuesta (Explainable AI - XAI).

## 13. Notificaciones
* No aplica, proceso sincrónico o asincrónico por WebSockets.

## 14. Criterios de aceptación (BDD)
* **CA-01: Auto-Corrección Matemática**
  * *Given* que el Agente de Física generó un problema con variables que resultan en División por Cero
  * *When* el Enjambre entra en fase de Validación
  * *Then* el Agente Matemático debe rechazar la respuesta, forzando una re-generación antes de mostrarla al usuario final, demostrando tolerancia a fallos por alucinación.
* **CA-02: Control de Costos (Token Limit)**
  * *Given* un debate multi-agente
  * *When* el costo acumulado de tokens supera los $0.10 USD en un solo request
  * *Then* el Orquestador debe hacer un *Hard Stop*, devolver el mejor resultado parcial y emitir una métrica de "Presupuesto Excedido".
