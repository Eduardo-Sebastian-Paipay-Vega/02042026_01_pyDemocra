## 2. Descripción funcional
* **Descripción:** Sistema de orquestación legal que, una vez que el padre/tutor paga la matrícula, genera un contrato de prestación de servicios educativos en PDF y gestiona su firma digital certificada, integrándose con APIs de e-Signature (ej. DocuSign, HelloSign o firmas biométricas locales).
* **Objetivo:** Eliminar el papel en la matrícula anual, ahorrando costos logísticos y dándole un valor legal irrefutable (no repudio) al contrato del colegio.
* **Alcance:** Generación de plantilla de contrato con variables (Nombre, Montos), envío a API de firmas, y recepción de Webhook con el contrato firmado.
* **Actores:** Padre de familia (Firmante), Sistema (Orquestador), Proveedor de Firmas (Autoridad Certificadora).

## 3. Contexto
* **Precondiciones:** 
  1. Pago inicial completado (RF-008).
  2. Plantilla de contrato (Template) configurada en la API externa (ej. DocuSign Template ID) vinculada al Tenant.
* **Disparador:** La matrícula entra en estado `PENDING_SIGNATURE`.
* **Postcondiciones:** Documento PDF firmado alojado en el bucket inmutable del colegio. Matrícula activa.

## 6. Flujo funcional
### Flujo principal (Embedded Signing)
1. El usuario (padre) completa el pago del año. El frontend redirige a la pantalla "Firma tu Contrato".
2. NestJS detecta `enrollment.status = PENDING_SIGNATURE`.
3. NestJS llama a la API de DocuSign (u otro proveedor) enviando `template_args` para rellenar el contrato dinámicamente.
4. Solicita un "Embedded Signing View" (URL temporal válida por 5 minutos).
5. Frontend abre un Modal/Iframe con esta URL, donde el padre dibuja su firma.
6. El proveedor emite un Webhook síncrono al backend (`docusign/webhook`) avisando que el contrato fue firmado.
7. NestJS descarga el PDF final con el certificado criptográfico de firma incrustado, lo sube a Supabase Storage y actualiza la matrícula a `ACTIVE`.

### Flujos alternativos
* **FA-01: Firma Asíncrona (Email):** Si el padre cierra la ventana sin firmar, el sistema cae en *Fallback*. El proveedor envía un correo electrónico para que termine el proceso en diferido. El estado queda en `PENDING_SIGNATURE`.

### Flujos de excepción
* **FE-01: Contrato Rechazado:** Si el tutor marca "Decline to Sign", el webhook lo capta, anula la matrícula, e inicia el workflow automático de reembolso de pago (RF-008).

## 8. Reglas de negocio
* **RN-001 (Obligatoriedad):** El estudiante (dependiente) NO puede entrar a ningún curso hasta que su matrícula no esté en estado `ACTIVE`, lo cual solo ocurre cuando el contrato está `SIGNED`.
* **RN-002 (Inmutabilidad del Documento):** El archivo PDF firmado descargado por Webhook nunca debe ser modificado, y se guarda en un Bucket de Storage con políticas de inmutabilidad activas (ej. S3 Object Lock o RLS en Supabase Storage `update=false`).

## 9. Permisos y seguridad
* **Firmas de Webhooks (HMAC):** Para evitar que un usuario haga spoofing enviando un POST de "Documento Firmado" falso, el webhook debe validarse criptográficamente con la llave pública del proveedor (DocuSign Connect Key).

## 10. Persistencia
* **Tablas/Colecciones:** `legal_contracts`.
* **Transacciones:** Cuando el contrato se marca como `SIGNED`, la actualización de la matrícula y la creación de las cuotas de pago (`installments`) ocurre dentro de una transacción `BEGIN; COMMIT;`.

## 11. Integraciones
* **APIs de e-Signature:** DocuSign eSignature REST API, PandaDoc, o firmas biométricas gubernamentales.

## 12. Auditoría
* Todo cambio de estado del contrato deja un rastro en `contract_audit_logs`, incluyendo la IP del firmante y el timestamp oficial provisto por la Autoridad Certificadora.

## 13. Notificaciones
* Envío automático de correo: "Aquí tienes una copia legal de tu contrato de matrícula".

## 14. Criterios de aceptación (BDD)
* **CA-01: Interceptación de Webhook Falso**
  * *Given* un hacker intentando vulnerar el sistema enviando un payload falso de webhook
  * *When* el request llega a `/api/v1/webhooks/docusign` sin la cabecera HMAC correcta
  * *Then* la API rechaza con 401 Unauthorized y no afecta el estado de la matrícula.
* **CA-02: Transición de Matrícula (State Machine)**
  * *Given* una matrícula `PENDING_SIGNATURE`
  * *When* se valida exitosamente el Webhook de firma
  * *Then* la matrícula debe pasar atómicamente a `ACTIVE` y las facturas del año (`installments`) deben ser generadas.
