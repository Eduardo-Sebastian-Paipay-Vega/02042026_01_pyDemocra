## 2. Descripción funcional
* **Descripción:** Un motor inyectado a nivel global en la capa UI (React Provider) que transmuta la plataforma en tiempo real para adaptarse a estudiantes con discapacidades visuales (Daltonismo, Baja visión), motoras (Navegación pura por teclado/Switch access) y cognitivas (Dislexia, TDAH, TEA).
* **Objetivo:** Cumplir la normativa gubernamental (ADA / WCAG 2.2 Nivel AA) indispensable para que EDUCACION OS pueda participar en licitaciones públicas de software educativo estatal. Nadie se queda atrás.
* **Alcance:** Modificadores de CSS (Variables), Tipografía Dinámica (OpenDyslexic), Reducción de animaciones, Screen Readers (ARIA).
* **Actores:** Estudiante con Diversidad Funcional (Usuario), Motor UI (Adaptador).

## 3. Contexto
* **Precondiciones:** 
  1. Diseño del sistema (Design System) construido usando variables CSS relativas (rem, em) y Paletas de Contraste > 4.5:1.
* **Disparador:** El estudiante configura sus preferencias de accesibilidad en su primer login, o las hereda del perfil del SO.
* **Postcondiciones:** La interfaz de toda la plataforma muta permanentemente para ese usuario.

## 6. Flujo funcional
### Flujo principal (Adaptación para Dislexia y TDAH)
1. María (Alumna con Dislexia y TDAH) ingresa a la plataforma.
2. Accede a las "Opciones de Accesibilidad" (Icono universal).
3. Activa: "Fuente para Dislexia", "Mayor Espaciado" y "Modo Enfoque (Focus Mode)".
4. El React Context actualiza el estado global.
5. Inmediatamente, la fuente global (Inter) cambia a `OpenDyslexic` (letras con bases más pesadas). El interlineado (line-height) aumenta de `1.5` a `2.0`.
6. El Modo Enfoque desactiva los Widgets gamificados laterales (Rankings, Monedas) que causan distracción severa en perfiles TDAH, dejando la pantalla en un modo de lectura zen (Zen Mode) puramente académico.

### Flujos alternativos
* **FA-01: Detección Automática del SO:** Si el teléfono o PC del alumno ya tiene configurado `prefers-reduced-motion: reduce` a nivel Sistema Operativo, EDUCACION OS lo respeta automáticamente usando Media Queries CSS, deshabilitando todas las animaciones Lottie y transiciones bruscas sin que el alumno tenga que hacer clic en nada.

## 8. Reglas de negocio
* **RN-001 (Independencia del Color):** Nunca se debe usar SOLO el color para transmitir información (ej. Texto verde para "Aprobado" y rojo para "Reprobado" jodería a un daltónico). Siempre debe ir acompañado de un ícono (✅ ❌) y un texto oculto para Screen Readers (`sr-only`).
* **RN-002 (Navegación 100% Teclado):** Es un requerimiento estricto que cualquier flujo (Hacer un examen, pagar una pensión) pueda completarse usando ÚNICAMENTE la tecla `Tab`, `Enter` y `Espacio`, garantizando accesibilidad motora (Focus Traps en Modales).

## 9. Permisos y seguridad
* **Auditoría UI:** Los componentes de Tailwind/Shadcn deben estar obligatoriamente wrappeados en primitivas de Radix UI que garantizan la gestión del estado ARIA (`aria-expanded`, `aria-hidden`) por defecto.

## 10. Persistencia

## 14. Criterios de aceptación (BDD)
* **CA-01: Focus Management en Modales**
  * *Given* que el usuario presiona un botón que abre un Modal de "Enviar Tarea"
  * *When* el Modal se abre
  * *Then* el foco del teclado (`document.activeElement`) debe moverse al primer input del Modal. Si el usuario presiona `Tab`, el foco debe estar "Atrapado" (Focus Trap) dentro del Modal y no navegar hacia los elementos de fondo, hasta que presione `Escape`.
* **CA-02: Soporte Lector de Pantallas (Aria-Live)**
  * *Given* un sistema de notificaciones P2P en vivo (RF-033)
  * *When* llega una nueva notificación Toast
  * *Then* el componente contenedor debe tener el atributo `aria-live="polite"`, permitiendo que VoiceOver/NVDA le lea la notificación al usuario invidente sin interrumpir su escritura actual.
