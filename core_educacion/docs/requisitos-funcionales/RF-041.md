## 2. Descripción funcional
* **Descripción:** Implementación de un Learning Record Store (LRS) nativo que soporta el estándar `xAPI (Experience API)` y `CMI5`. Esto permite que cualquier actividad de aprendizaje (leer un libro en Kindle, hacer un simulador en Unity, o ver un documental de Netflix) pueda reportar su progreso de vuelta a EDUCACION OS usando el formato estandarizado "Actor-Verbo-Objeto" (Ej. "Juan-Completó-Simulador de Vuelo").
* **Objetivo:** Romper las paredes del LMS tradicional. El aprendizaje ocurre en todas partes, no solo dentro del software de la escuela. EDUCACION OS actúa como el hub centralizador de toda la vida académica del usuario.
* **Alcance:** Endpoint xAPI, Validación de Statements, Data Lake de Experiencias.
* **Actores:** Activity Provider (Tercero), LRS (Receptor), Estudiante (Actor).

## 3. Contexto
* **Precondiciones:** 
  1. RF-034 (OAuth2) para autenticar a los proveedores externos.
  2. Alumno registrado con un Identificador Universal.
* **Disparador:** Un sistema externo envía un Payload JSON al endpoint `/xapi/statements`.
* **Postcondiciones:** El "Statement" se valida y se inserta inmutablemente en el LRS (Data Warehouse).

## 4. Entradas
| Parámetro | Tipo | Obligatorio | Validaciones |
| :--- | :--- | :---: | :--- |
| `actor` | JSON | Sí | Debe coincidir con el correo o ID del alumno. |
| `verb` | JSON | Sí | URL del verbo estandarizado (Ej. `http://adlnet.gov/expapi/verbs/completed`). |
| `object` | JSON | Sí | Actividad realizada. |
| `result` | JSON | No | Score, éxito, duración. |

## 5. Salidas
| Resultado / Campo | Tipo / Estado | Mensaje |
| :--- | :--- | :--- |
| `statement_id` | UUID | UUID generado para el statement. |
| HTTP Status | 200 OK | Confirmación de ingesta. |

## 6. Flujo funcional
### Flujo principal (Ingesta xAPI)
1. El estudiante usa una App de Realidad Virtual externa para explorar el Sistema Solar.
2. Al terminar, la App VR envía un Statement a EDUCACION OS: `{"actor": {"mbox": "mailto:juan@school.edu"}, "verb": {"id": "http://adlnet.gov/expapi/verbs/experienced"}, "object": {"id": "urn:vr:solar-system"}}`.
3. El API Gateway recibe el POST. Valida el token OAuth2 de la App VR.
4. El servicio LRS valida que el JSON cumpla estrictamente con el esquema IEEE 9274.1.1 (xAPI 2.0).
5. Se inserta en la base de datos (Postgres JSONB o MongoDB).
6. Un worker asíncrono toma este Statement y lo inyecta en el Gemelo Digital (RF-038) sumándole puntos de "Afinidad Visual/Interactiva" al estudiante (RF-032).

### Flujos de excepción
* **FE-01: Statement Malformado:** Si el JSON no cumple el estándar (ej. falta el ID del verbo), el LRS lo rechaza con HTTP 400. xAPI es un estándar inmutable; un statement nunca se actualiza (UPDATE), si hay un error, se envía un statement de anulación (Voiding).

## 8. Reglas de negocio
* **RN-001 (Inmutabilidad del Statement):** Por norma de ADL (Advanced Distributed Learning), un statement xAPI insertado NUNCA puede ser modificado ni borrado (Append-only). 
* **RN-002 (Resolución de Identidad):** El sistema debe reconciliar el "Actor" del statement (que puede ser un correo electrónico o un OpenID) con el UUID interno del alumno en la tabla `users` de forma segura.

## 9. Permisos y seguridad
* **Políticas LRS:** El endpoint de xAPI debe estar protegido contra inyecciones NoSQL/JSON y soportar un throughput altísimo, aislando este tráfico del API core de la plataforma escolar para no degradar el rendimiento principal.

## 10. Persistencia
* **Tablas/Colecciones:** Bases de datos de documentos (MongoDB) o PostgreSQL con columnas `JSONB` e índices GIN (Generalized Inverted Index) para búsquedas veloces dentro del JSON.

## 11. Integraciones
* **Validadores:** `xapi-statement-validator` (Librería Node.js para check de sintaxis).

## 12. Auditoría
* Trazabilidad 100% auditable. Cualquier plataforma de e-learning del mundo puede auditar a EDUCACION OS si cumple el estándar oficial LRS.

## 13. Notificaciones
* No aplica (Silencioso).

## 14. Criterios de aceptación (BDD)
* **CA-01: Inserción y Validación xAPI**
  * *Given* un payload xAPI 2.0 válido
  * *When* se envía al endpoint `/xapi/statements`
  * *Then* el sistema debe devolver 200 OK y retornar un UUID generado para el statement.
* **CA-02: Voiding (Anulación)**
  * *Given* un statement emitido por error
  * *When* el proveedor envía un nuevo statement con el verbo "Voided" apuntando al UUID anterior
  * *Then* el sistema debe marcar lógicamente el statement original como anulado sin eliminarlo físicamente de la base de datos (Compliance).
