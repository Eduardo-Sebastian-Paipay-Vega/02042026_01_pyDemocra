# RF-013: Circulares Oficiales y Anuncios Institucionales

| Atributo | Detalle |

| **Módulo** | Comunicación / Administrativo |

| **Versión** | 1.0 |
| **Estado** | AUDITED (Enriquecido) |
| **Prioridad** | Media |

## 2. Descripción funcional
* **Descripción:** Tablón central de anuncios del colegio o academia (Tenant), que permite a Directores y Coordinadores publicar comunicados oficiales (circulares) con adjuntos, segmentando a quién va dirigido (Todos, Solo Padres, Solo Profesores, Curso A). Además, requiere firma o confirmación de lectura digital.
* **Objetivo:** Centralizar la comunicación burocrática e institucional reemplazando el uso de correos sueltos o WhatsApp, garantizando evidencia legal de que el anuncio fue leído ("acuse de recibo").
* **Alcance:** Creación del anuncio (WYSIWYG editor), segmentación del público objetivo, seguimiento de lecturas, y envío paralelo por correo.
* **Actores:** Director/Admin (Emisor), Apoderado/Docente/Estudiante (Receptor).

## 3. Contexto
* **Precondiciones:** 
  1. Rol `DIRECTOR` o `ADMIN` activo para crear.
  2. Público segmentado correctamente mediante cohorts o grupos en la base de datos.
* **Disparador:** Publicación de una circular desde el panel administrativo.
* **Postcondiciones:** Registros de envío generados en `announcement_recipients`. Notificaciones despachadas.

## 4. Entradas
| Parámetro | Tipo | Obligatorio | Validaciones |
| :--- | :--- | :---: | :--- |
| `title` | VARCHAR(150) | Sí | - |
| `content` | TEXT | Sí | Rich HTML (Sanitizado con DOMPurify/Zod). |
| `target_audience`| JSONB | Sí | Reglas de filtrado (ej. `{ role: "parent", grade: "5A" }`). |
| `require_ack` | BOOLEAN | Sí | Si requiere confirmación de lectura (Acuse). |
| `attachments` | ARRAY | No | Hasta 5 archivos (PDF, JPG). Límite 10MB c/u. |

## 5. Salidas
| Resultado / Campo | Tipo / Estado | Mensaje |
| :--- | :--- | :--- |
| `announcement_id`| UUID | ID del comunicado creado. |
| `dispatch_stats` | JSON | "Enviado a 150 usuarios. 120 correos entregados." |

## 6. Flujo funcional
### Flujo principal (Creación y Despacho)
1. El Administrador del Tenant redacta la circular en el editor y presiona "Publicar".
2. NestJS guarda el anuncio en `tenant_announcements`.
3. Un Background Job (BullMQ) evalúa las reglas de `target_audience`.
4. El Job hace un `SELECT` de todos los UUIDs de usuarios que cumplen la regla.
5. Se inserta en bloque (Bulk Insert) en `announcement_recipients` (Mapeo de quién debe leerlo).
6. Se disparan eventos de notificaciones (RF-012) para cada usuario y se encolan correos electrónicos con el resumen de la circular.

### Flujos alternativos
* **FA-01: Acuse de Recibo Obligatorio (Interstitials):** Si `require_ack = true`, la próxima vez que el usuario afectado haga Login, no verá el Dashboard principal, sino una pantalla completa ineludible (Interstitial/Modal) con el anuncio y un checkbox: "Declaro haber leído esta circular".

### Flujos de excepción
* **FE-01: Anulaciones Rápidas:** Si el director nota un error y borra el anuncio a los 30 segundos, el sistema emite un evento `RECALL` que intercepta la cola de RabbitMQ y destruye los correos que aún no han salido.

## 8. Reglas de negocio
* **RN-001 (Derecho de Borrado):** Los anuncios oficiales enviados con Acuse de Recibo firmado por al menos 1 usuario NO pueden ser borrados (hard delete). Solo pueden ser archivados o marcados con una nota de corrección, por razones de auditoría legal (Compliance).
* **RN-002 (Segmentación Matemática):** La regla de `target_audience` se compila a un Query dinámico (Knex/Prisma) que intercepta automáticamente tablas como `enrollments`, `user_roles`, o `cohorts`.

## 9. Permisos y seguridad
* **Políticas RLS:** 
  ```sql
  CREATE POLICY "Usuarios ven anuncios dirigidos a ellos" ON tenant_announcements
  FOR SELECT USING (
    EXISTS (SELECT 1 FROM announcement_recipients ar 
            WHERE ar.announcement_id = tenant_announcements.id 
            AND ar.user_id = auth.uid())
  );
  ```

## 10. Persistencia
* **Tablas/Colecciones:** `tenant_announcements`, `announcement_recipients`.
* **Carga Masiva:** Si el colegio tiene 5000 alumnos, insertar en `announcement_recipients` se hace vía PostgreSQL `COPY` o `INSERT INTO ... VALUES` particionado en batches de 1000 para no bloquear la BD.

## 11. Integraciones
* **Almacenamiento de Archivos:** Supabase Storage.
* **Emails:** Resend/SendGrid para envíos masivos.

## 12. Auditoría
* Panel en vivo para el Director ("Insights de Lectura") con un Pie Chart mostrando % de Leídos vs No Leídos, y botón para "Re-enviar recordatorio a no lectores".

## 13. Notificaciones
* Notificación push in-app y envío por correo del comunicado.

## 14. Criterios de aceptación (BDD)
* **CA-01: Intercepción de Login (Acuse obligatorio)**
  * *Given* que el usuario tiene un anuncio marcado como `require_ack = true` pendiente de lectura
  * *When* completa su proceso de Auth (Login) exitosamente
  * *Then* el frontend le redirige a `/announcements/pending` bloqueando acceso a cualquier otra ruta del Dashboard hasta que firme digitalmente.
* **CA-02: Generación correcta de audiencia**
  * *Given* una audiencia objetivo "Grado 5" (40 estudiantes)
  * *When* el director publica la circular
  * *Then* se deben haber creado exactamente 40 filas en la tabla `announcement_recipients` correspondientes a esos UUIDs y a nadie más.

## 15. Casos de prueba relacionados
